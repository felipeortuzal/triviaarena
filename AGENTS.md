# Riviera Showdown

Este repositório é a fonte de continuidade do projeto. O nome público é **Riviera Showdown**. A implementação inicial está em `felipeortuzal/triviaarena`. Responda a Felipe em português do Brasil.

## Quando Felipe disser “execute etapa N”

1. Resolva o número no [índice de execução](docs/etapas/README.md). Aceite “etapa1”, “etapa 1”, “etapa 01” e equivalentes sem diferenciar maiúsculas. Para “retome a etapa N”, use o registro de progresso e continue da primeira pendência após verificá-la. Uma consulta de status pede apenas leitura e relato. Um pedido para executar autoriza implementar, testar e salvar aquela etapa. Se Felipe indicar mais de uma, siga a ordem de dependência e reporte cada resultado.
2. Leia o prompt integral, a linha de progresso e o código vigente no GitHub. Confira branch padrão, último commit e mudanças desde o marco anterior. Em uma conversa nova, esses arquivos permitem retomar. Se a etapa já passou, confira os critérios na versão vigente e corrija apenas regressões ou pendências. Se falta um pré-requisito, faça a parte independente autorizada e indique a dependência concreta para o restante.
3. Use as funções e os dados existentes quando adequados. Faça alterações pequenas que possam ser revisadas. Mantenha os dois jogos e o modo misto recuperáveis durante a migração. Na versão pública, exponha como jogáveis apenas modos habilitados e verificados. Se surgir um conflito com outro commit, releia a versão nova e preserve as duas intenções.
4. Trabalhe pelo conector oficial do GitHub quando disponível. Atualize a branch padrão com mudanças revisadas quando permitido. Se a proteção da branch exigir PR, abra-o, registre o endereço e indique o que falta integrar. Preserve o histórico. Renomear o repositório, apagar dados reais ou contratar serviço pago exige decisão explícita de Felipe. Use configurações públicas do web app quando necessárias. Credenciais administrativas e tokens ficam fora do Git e dos relatórios.
5. Execute testes pertinentes pelo caminho usado pelo jogador. Diferencie teste de função, emulador, navegadores independentes, publicação e dois aparelhos físicos. Identifique o ambiente e o resultado de cada teste. A aprovação do multiplayer exige partida real entre aparelhos diferentes. Enquanto faltar um aparelho ou acesso, deixe o teste marcado como pendente e prossiga com o trabalho independente.
6. Atualize a linha correspondente do [índice](docs/etapas/README.md) no mesmo conjunto de mudanças. Use os estados “A executar”, “Parcial”, “Validada” ou “Bloqueada”. Registre o que passou, o que falta e o próximo ponto de retomada. Para execução em PR use o link do PR ou da execução de CI, se conhecido. Informe o SHA final na resposta depois que o GitHub confirmar a escrita. Evite commits apenas para referenciar o próprio SHA.
7. Em atualizações do jogo entregue um arquivo HTML autocontido para baixar e abrir por duplo clique, gerado da mesma revisão do frontend. Se a alteração for só de infraestrutura, valide e disponibilize a prévia vigente. O modo local precisa identificar o que pode ser testado em um aparelho. Forneça também o link HTTPS quando houver publicação confirmada. Confira o arquivo oferecido, o link de convite e o caminho do projeto no Pages. Evite ZIP.
8. Ao terminar, responda com o resultado, links para a prévia e para o site quando disponível, commit ou PR, testes e pendência concreta. Execute a próxima etapa quando Felipe a pedir.

Se faltar uma permissão externa, tente primeiro o caminho autorizado disponível. Entregue o código e os testes já possíveis e descreva a ação externa mínima, com o local e o sinal de sucesso. Um serviço simulado serve para desenvolvimento e testes.
